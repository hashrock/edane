# WebMCPとノート同期

## 編集経路

トップレベルのエディタページで `document.modelContext` が提供されている場合、
`get_note` と `apply_note` を登録する。閲覧専用ページは読み取りだけを登録する。
ツールの編集も画面の編集も既存の editorReducer → dispatch を通る。
登録解除はページのunmount時に行う。非対応ブラウザでも通常のUIは使える。

reducerの前後差分をノード属性と子の並びの操作として送信する。
ノートIDごとのNoteRoom Durable ObjectがWebSocketと旧PUT APIを共通の順序に並べる。
D1を永続的な正本とし、内容・version・操作IDの受領記録を同一トランザクションで更新してから配信する。
非公開内容には従来の暗号化を適用し、DOストレージに平文のコピーは置かない。
公開ページ・一覧など既存のD1読み取りも確認済みの更新を読める。

## 競合規則

- 別ノード／別属性の変更は併合する。
- 同じ属性を古い値から変更する操作は競合として拒否する。文字単位のCRDTではない。
- 同じ親への独立した追加はどちらも残す。同じ位置への追加順はサーバー到着順。
- 同じ兄弟集合の競合する並べ替え、循環、複数親、孤立ノードは拒否する。
- 削除対象が別クライアントで変更された場合は削除を拒否する。
  削除済みノードへの変更・子追加も拒否し、暗黙に復活させない。
- バッチは全体適用または全体拒否。拒否した操作は画面の復元用欄に残す。
- Undo/Redoは履歴の逆差分を最新状態に適用し、他クライアントの無関係な変更を維持する。
  同じ項目の競合時にはUndoを拒否して履歴を残す。

クライアントは未確認操作を楽観表示し、一度に1操作を送る。
切断後は最新スナップショットを受け取り、同じ操作IDで再送する。
受領記録がある操作は再適用しない。IDを異なる内容で再利用することも拒否する。
受領記録は直近 1000 版分を残し、100 版ごとに古いものを消す（`app/sync/limits.ts`）。
それより古い id の再送は新しい commit として扱われ、多くは競合として拒否される。
未確認操作と拒否操作の復元データはページのメモリ内だけに保持する。
ブラウザ終了・強制再読み込みをまたぐオフライン復元は未実装。

## 暴走・課金の上限

値と根拠は `app/sync/limits.ts` と `app/components/noteSyncClient.ts`。

- NoteRoom は WebSocket の hibernation API（`acceptWebSocket`）を使い、alarm も DO 間呼び出しも持たない。
  接続中でも無通信なら duration 課金されない。
- 1 ノートの同時接続は 32 本まで（超えたら upgrade を 429、D1 を読む前に断る）。
- WebSocket の commit はノートごとのトークンバケット（容量 300・補充 50 件/秒、全接続で共有）。
  超えた接続は 4429 で閉じる。未確認操作はクライアントに残り、再接続後に再送される。
- クライアントの再接続は 500 ms から倍々で最大 30 秒。30 秒以上続いた接続のあとだけ最初に戻す
  （受け付けてすぐ閉じられるループで 500 ms 間隔にならないように）。4404（ノートがゴミ箱・削除）では再接続しない。
  未確認操作がページにしか無いので試行回数の上限は設けない。
- id の無い error（読めなかったメッセージ）は送信中の commit への拒否として扱う（再送の無限ループを防ぐ）。
- 旧 PUT・リモート MCP は HTTP 1 リクエストあたり高々 1 commit（MCP は JSON-RPC バッチ 20 件まで）で、
  リクエスト課金の範囲に収まるので NoteRoom 側の上限はかけない。

## 互換性と展開

D1 migration `0010_note_sync.sql` と Wrangler の `NOTE_ROOMS` binding /
`note-sync-v1` migration が必要。今回、本番への適用はしていない。

旧 `PUT /api/notes/:id` は `version` 必須（不足は428、不一致は409）。
`GET /api/notes/:id/sync` で現状とversionを取得する。
古い全体保存クライアントを無条件に受け入れると同期の保証が失われるため、
旧クライアントは更新が必要。内容が変わらない PUT は commit せず、version を進めない。

## リモートMCP（#205 / #207 で統合）

リモートMCP（`POST /mcp`）の編集も同じ NoteRoom を通る。ブラウザと違い、差分ではなく依頼そのもの
（`NoteEditRequest`）を `NoteRoom.applyEdit` に渡し、NoteRoom がその時点の最新状態に1つの順番の中で当てる。
したがってエージェントの編集は到着順に最新状態へ当たり、エージェントが以前に読んだ値との競合は検出しない
（ブラウザの未確認操作のような「読んだ時点」が無いため）。存在しないノードへの編集は拒否する。
任意の `operationId` で再送を1回にまとめる（受領記録のダイジェストは依頼から取る）。
NoteRoom の想定内の拒否は例外ではなく型付きの結果（`RoomResult` / `RoomRejection`）で返す。

## 検証（2026-10-22時点）

- TypeScriptとビルド、既存Nodeテスト全件を実行。
- 操作単体テスト：独立編集、同じ項目の競合、同時追加、削除との競合、Undo/Redo、入力検証。
- 既存の全EditorAction生成器によるプロパティテスト：reducerの変更を差分送信して再現できること。
- ローカルWorker + D1 migrationを起動。内蔵ブラウザで新しいテストノートを作成。
- WebMCPの自動発見、get_note、apply_noteを実際に呼び出し、保存確認後のversion=1を確認。
- 独立した2つ目のタブから別ノードを編集し、両方の変更を含むversion=2のツール結果を確認。
- その後、ブラウザの自動承認レビューが利用上限で停止した。
  元タブへの反映の再確認、実通信での競合・切断再送・Undo、ブラウザ回帰テストは未完了。
- 本番デプロイ・本番データを使った検証はしていない。
